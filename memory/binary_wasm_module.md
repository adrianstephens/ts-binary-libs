## What it is

`binary-libs/src/wasm.ts`, exported as `@isopodlabs/binary_libs/wasm` (added to that package's `package.json` `exports` map). A real WebAssembly binary format module -- reads *and* writes (unlike the rest of `binary-libs`, which is read-only: elf.ts/pe.ts/mach.ts/etc only ever introspect existing binaries; wasm needed writing too, to serve as [[tison_towasm]]'s assembler). Covers: module preamble, all standard sections (type/import/function/table/memory/global/export/start/element/code/data/datacount/custom), the full core instruction set (control/reference/parametric/variable/table/memory/numeric), bulk-memory + reference-types + multi-value + sign-extension, the finalized **GC proposal** (`0xFB`-prefixed), SIMD (`0xFD`-prefixed) and threads/atomics (`0xFE`-prefixed) -- all stable in Wasm 2.0/3.0. This note (2026-07-26) originally said SIMD/atomics/exception-handling were deliberately unsupported; that's stale -- SIMD/atomics were added later, and **exception-handling** (tag section id 13, `throw`/`throw_ref`/`try_table`+`catch`/`catch_ref`/`catch_all`/`catch_all_ref`, `tag` export/import kind) was added 2026-08-18, closing [[tison_towasm_exceptions_prereq_research]]'s prerequisite gap. Targets the current (exnref/`try_table`) proposal, not the deprecated legacy `try`/`catch`/`delegate` one -- consistent with `ABSTRACT_HEAP` already having `exn`/`noexn` heap types before this work started. Verified via a real independent validator (`wasmtime run`, not just self-consistent round-trip): a hand-built module using a declared tag, `throw`, `try_table` with `catch`/`catch_all` compiled and executed correctly (including tag-payload delivery through `catch`), and `throw_ref`/`catch_ref`/`catch_all_ref` round-tripped byte-identical. One correctness subtlety hit while writing the test module, not a bug in wasm.ts: `catch_all`/`catch_all_ref` deliver *zero* values when branching, so their label target must itself have an empty result type -- `wasmtime` rejects `(catch_all $L)` where `$L` expects a result, exactly per spec.

**Real bug found+fixed same day, later session (multi-value `BlockType`)**: `BlockType`'s `{typeIndex: number}` case (used for multi-result blocktypes) was silently corrupted on write -- `RawType`'s own `number` case *is* the wire encoding for a type-index blocktype, but `BlockType`'s `bin.as(RawType, ...)` call supplied no reverse (`from`) function, so a `{typeIndex}` value passed straight through to `RawType.put` unchanged, where the generic `typeof val === 'object'` branch (meant for `ValType`'s `{ref, nullable}` shape) silently misread it as that shape instead (both `.ref`/`.nullable` undefined -> wrote 2 garbage bytes, losing the real index). Never triggered before since nothing produced a multi-value blocktype until [[tison_wat_parser_exceptions]]'s multi-value-blocktype generalization exercised it. Fixed by adding the missing `from` (unwrap `{typeIndex}`->number) and correcting `get`'s wrap (bare positive number -> `{typeIndex: v}`, previously passed through raw, violating the exported TS type). Verified against real `wasmtime`. Full details in [[tison_wat_parser_exceptions]].

Born out of a size complaint, not a feature request: [[tison_towasm]] originally went through WAT text + `binaryen` as an external assembler; `binaryen`'s `node_modules` footprint (~93MB, vs. tison's own ~480KB) was flagged as disproportionate for "assemble text into bytes." The reframe: tison's `towasm.ts` fully controls its own instruction set (never parses arbitrary external wasm), so what was actually needed was a first-party *writer* the user could own, in the style of their existing binary-format collection (elf.ts/pe.ts/mach.ts) -- and Node's own `WebAssembly.Module` already validates/executes wasm-GC binaries natively with zero flags, so no external validator/runtime was needed either, only the encoder.

## Design notes worth remembering

- **First draft leaned on hand-written `{get, put}` objects far more than it should have** -- the user's own correction, mid-review: "using custom get and put functions should be a last resort," demonstrated by rewriting `HeapTypeT` as `bin.as(SLEB128, toFn, fromFn)` instead of a bespoke object. Applied throughout after that: `ValTypeT`/`StorageTypeT` became `bin.Switch(bin.UINT8, table, discriminatorFn)` over a byte->`Type` lookup table (`Const` for byte-is-the-whole-value cases, `as` for "read one more thing and transform"); `FieldTypeT`/`GlobalTypeT`/etc became plain `bin.Struct({...})` object specs. Even the peek-based `SubType`/`RecType` logic (originally hand-rolled lookahead) turned out to be expressible as `Switch` too: each nests the OTHER's untagged payload specs (e.g. `CompTypeT`'s own per-kind specs, reused bare so `SubTypeT`'s switch table can inject the implied `final`/`supertypes` for a bare comptype byte) rather than ever calling the already-tag-consuming outer `TypeT` a second time -- the trick that makes 3 levels of "leading byte picks the shape" collapse into flat tables with no double-reads. `Switch`'s default discriminator (`Discriminator`, in `binary`'s own types.ts) only tells alternatives apart by matching object *field names*, which is useless when values are plain strings or all shaped alike (`{ref, nullable}`) -- every one of these needed an explicit discriminator function, used only for writing (reading just dispatches on the byte actually present).
- **The whole module-level section loop became one declarative spec too**, once the user reworked `WasmModule` itself: `bin.RemainingRepeat({id: bin.UINT8, _: bin.Merge(bin.Size(U32, bin.Switch(s => s.lookupObj('id'), {...simple per-id object specs...})))})`, wrapped in an outer `bin.Merge`, replacing what had been an imperative `while` loop entirely. `WasmModule extends bin.Class(WasmSpec)` gets read/write/`get`/`put`/property-based construction for free, matching every other format in this collection (elf.ts's `Phdr`/`Shdr`, etc.).
- **What's still genuinely hand-written, and why**: only the instruction stream (`InstrT`/`putInstr`/`readInstrsUntil`). Block/loop/if bodies nest to a data-dependent depth terminated by a matching `0x0B end`/`0x05 else`, not a length prefix -- real recursive-descent, the same scope choice the `binary` package's own `ULEB128`/`RemainingRepeat` make internally for similarly-shaped problems. `Instr = {op: string, imm?, body?, body2?}`, not a ~150-way discriminated union (its own few hundred lines of type declarations for little real benefit); `imm`'s shape is documented per opcode table instead. Also `BlockType`'s leading byte is the one place even a *value* type genuinely can't become a `Switch`: a real type-index's own first SLEB128 byte would otherwise have to double as a dispatch key, so it stays a plain `isValTypeByte` membership peek (checking valtype bytes first, same precedence the spec itself uses).
- **`bin.Class`-based construction leaves read-only artifacts on the instance** that a directly-constructed (from a plain data object) instance never has: `magic`/`version` (present as own keys valued `undefined` -- `Expect`'s own read result is always `undefined`, but the key still gets assigned), an outer `Merge`'s own placeholder (`_`, always `{}`), and `id` (the *last* repeated section's id byte, since `id` is a real named field in the per-iteration spec, not itself hidden behind `_`). None of this showed up until `assert.deepStrictEqual`-based round-trip testing (write→read→compare) was added -- execution-only testing never touches instance shape. Fixed with a custom `WasmModule` constructor that deletes exactly those four keys after `super()`, only on the "read from a stream" path (not the "construct from a data object" path, which never has them). Same constructor also restored the two conveniences a `bin.Class` base doesn't give you for free: `new WasmModule()` with no args (sensible all-arrays-empty defaults, for build-then-mutate callers like [[tison_towasm]]), and accepting a raw `Uint8Array` directly (wrapped in `new bin.stream(...)` internally) instead of requiring the caller to do that first.
- **`heaptype` is uniformly a signed LEB128 (s33)**: non-negative = concrete type index, small negative = one of a fixed set of abstract heap types (`func`/`extern`/`any`/`eq`/`i31`/`struct`/`array`/`none`/`nofunc`/`noextern`/...). Those negatives aren't arbitrary -- they're exactly `byte - 0x80` for the single-byte reftype shorthand bytes (`funcref`=0x70 etc.), which is *why* a bare reftype byte and a 1-byte heaptype SLEB128 decode identically. Wrote a hand-rolled `SLEB128` (the `binary` package only had `ULEB128`) for this and for `i32.const`/`i64.const`.
- **Element segments (flags 0-7) got a confused-then-corrected first draft**: the real rule is bit0=passive/declarative vs active, bit1 means different things depending on bit0 (explicit-table vs. declarative), bit2=expr-init-with-reftype-tag vs funcidx-init-with-elemkind-tag, *except* flags 0 and 4 (active+implicit-table) which omit the type tag byte entirely (always funcref). First implementation had dead/contradictory branches (including an `as unknown as ValType` cast papering over the confusion -- a real instance of [[feedback_avoid_unsafe_casts]]'s exact concern); rewritten cleanly with the flags derived imperatively and no casts.
- **Round-trip fidelity needs care with optional fields**: `Limits.shared`/`ElemSegment.table`/`DataSegment.memory` etc. must be *omitted* from the reader's output object when absent, not set to `undefined`/`false` -- `assert.deepStrictEqual` (and just general hygiene matching the `?:`-optional interface declarations) treats `{x: undefined}` as different from `{}`. Caught by round-trip testing (write then read back, compare structurally), not by execution testing alone -- execution only exercises the *value* semantics, not exact object shape.
- **This surfaced two real, previously-uncovered bugs in the underlying `@isopodlabs/binary` package itself** -- see [[binary_package_bugs_found]]. Not implementation mistakes in wasm.ts; genuine correctness bugs in shared infra that elf.ts/pe.ts/mach.ts/cvinfo.ts also depend on, just never triggered them (mostly fixed-width fields, rarely a literal zero through `ULEB128`, rarely `Size`-wrapped content over 127 bytes with a variable-width length type).
- **`WasmModule`'s hand-written `write()` is NOT redundant, confirmed empirically**: the user asked whether it might "just work" from `WasmSpec` alone. Deleting it and relying on `bin.Class`'s auto-generated write crashed (`Cannot read properties of undefined (reading 'length')`) -- `RemainingRepeat`'s write-side (`SplitRepeat`) can't reconstruct the `id` discriminator byte the `Switch` needs, because that `Switch`'s discriminator (`s => s.lookupObj('id')`) is read-only by design. Restored from backup rather than chasing a deeper fix to `binary` itself.
- **Second full audit pass (same session, later)**: user asked "are these all cases that can't be done using bin.Struct or bin.as?" and separately "there shouldn't be a hand-written type/interface *and* a spec; the interface should always be inferable from the spec." Converted essentially everything to `bin.ReadType<typeof X>`-derived types (no paired hand interface): `ValType`, `HeapType`, `AbstractHeapType` (now derived from `ABSTRACT_HEAP`'s own keys, not hand-listed), `FieldType`, `CompType`, `SubType`, `Limits`, `GlobalType`, `TypeSection`, `ImportDesc`, `Import`, `Global`, `Export`, `ElemSegment`, `DataSegment`, `LocalsGroup`, `FuncBody`, `CustomSection`. Also derived `REFTYPE_SHORTHAND` from `ABSTRACT_HEAP` (`byte = key + 0x80`) instead of hand-duplicating the table -- another user catch. Single-use switch tables/discriminator functions got inlined as arrows at the `Switch(...)` call site per "prefer not to add type annotations where inferable, and single-use functions/objects to be inlined"; multi-use discriminators (`valTypeKey`, `compTypeKey`, `subTypeKey`) stayed as named functions typed `(v: any)` -- matching `Switch`'s own `discriminator?: (value: any) => K` signature -- since they're reused across multiple switches and can't name the very type they help construct without a real circular-type error.
- **`TableType` is a second genuinely-irreducible case, found the hard way**: naively deriving it via `ReadType<typeof TableType>` compiles, but silently produces the WRONG type. `ReadType`'s handling of a `Switch` whose branches structurally overlap (all 13 `TableType` branches share `reftype`/`limits`; only one has `init`) doesn't keep a clean discriminated union -- it *merges* the branches field-by-field (the exact mechanism `WasmSpec`'s own module-level section `Switch` relies on, to legitimately produce one `{types?, imports?, ...}` object). A field only comes out optional in that merge if its own type already includes `undefined`; `init: Instr[]` (required on its one branch) doesn't, so the merged result has `init` required on *every* table, breaking any table literal that omits it (caught by `test-wasm.ts`'s import/table/global/element/start round-trip test, not by `tsc` -- it compiled fine at every step). Fix: keep `export interface TableType {reftype,limits,init?}` hand-written, and add back `const TableType: bin.TypeT<TableType> = bin.Switch(...)` -- the explicit annotation isn't decorative, it's what forces the const's read type onto the correct shape instead of leaking the merged one into `TableSectionT`/`ImportDesc`/`WasmModuleData.tables`. Same bucket as `BlockType`/`Instr`: some shapes genuinely can't drop their hand-written type.

## Toolchain note

`binaryen`'s test usage needed an ESM-interop workaround (documented in [[tison_towasm]]) before being fully replaced -- kept as a historical note there, not relevant to `wasm.ts` itself, which has zero runtime dependencies of its own beyond `@isopodlabs/binary`.

Linked into `tison` via `npm link` (both `binary` and `binary-libs` are pre-publish, sibling-directory packages in this monorepo) -- `npm link <pkg>` sometimes materializes a **real copy** rather than a symlink (observed: a stale global-link-registry snapshot, predating a `package.json` `exports` edit, got copied into `tison/node_modules/@isopodlabs/binary_libs` instead of a live symlink). If a linked package's changes don't seem to take effect, check `ls -la node_modules/@isopodlabs/` for an actual symlink vs. a real directory before assuming the edit itself is wrong -- fixed by deleting and hand-creating the symlink (`ln -s ../../../binary-libs binary_libs`) rather than trusting `npm link` a second time.

Also needed a targeted `tsconfig.json` `"paths"` entry (`"@isopodlabs/binary_libs/wasm": ["../binary-libs/dist/wasm"]`) in `tison`'s root tsconfig: classic/"node10" module resolution (the default under `module: commonjs`, which `tison` uses) predates `package.json` `exports` map support entirely, so `tsc`/`ts-node` can't see the `./wasm` subpath export even though Node's own runtime `require()` resolves it fine. Same class of gotcha as the async-module-graph one already noted for `binaryen` -- TS's own module resolution algorithm choice, independent of whether the package itself is set up correctly.
